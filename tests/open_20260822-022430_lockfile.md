# Test spec — #31: committed package-lock.json

**Source task:** #31 (fix: commit package-lock.json so `npm ci` works)
**Code under test:** repository state (`.gitignore`, `package-lock.json`) — the
"behavior" is a reproducible-install invariant, not a code path.

## Behaviors to verify

- `package-lock.json` is tracked in git and not matched by `.gitignore`.
- Fresh-clone `npm ci && npm test` is green (verified at commit time: 15/15).
- Lockfile stays in sync with `package.json`: adding/changing a dependency
  without regenerating the lockfile breaks `npm ci` — that's the regression
  signal, enforced by CI running `npm ci` (#14), not by a unit test.

## Edge cases

- Developer commits an updated `package.json` but forgets the lockfile → CI
  `npm ci` failure is the intended detector; pin this in CI rather than a
  pre-commit hook (no hook infra in the repo).
- Node/npm version drift: lockfileVersion 3 requires npm ≥ 7; document the
  floor if CI pins a different Node version (#14's call).

## How to run

Fresh clone + `npm ci && npm test`; once #14 lands, CI runs exactly this.

## Notes

#2's original DoD ("fresh-clone `npm ci && node tools/validate.mjs` succeeds")
was silently broken by the ignored lockfile — this test spec exists to keep
that class of regression visible rather than relying on session reports.
