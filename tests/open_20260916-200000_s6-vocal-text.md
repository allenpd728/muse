# Test spec — S6 vocal text (task #318)

Written 2026-09-16 by the completing agent, per TASK_WORKFLOW §6.

## What landed (behavior under test)

Vocal text is now part of the score, not dropped at parse time.

| Layer | Change |
|---|---|
| IR (`muse_ir.model.Note`) | `lyric: str|None`, `syllabic: str|None`, `extend: bool`; `lyric` added to `sort_key()`; validation for unknown `syllabic` and empty-string lyrics |
| Parser (`musicxml.py`) | `_parse_lyric()` reads `<lyric>`; verse 1 is carried, extra verses and unknown `<syllabic>` values are dropped **with a warning** |
| Roll (`muse_roll.roll`) | presence-bitmap bits 5–7; lyric/syllabic interned via the existing string table |
| Chain | `_canonical()` now includes the three fields, so a dropped or altered lyric **fails** the pipeline instead of passing |

Carrier choice: option (a) from the issue — first-class optional fields on the
note. It fits the existing presence-bitmap design exactly (bits 5–7 were free),
keeps a note's text adjacent to the note, and needed no container change.
Recorded in `FORMAT_SPEC.md` §4.6 with §8's open question closed.

Coverage: `tools/ir/tests/test_vocal_text.py` (12 tests) and
`tools/muse_roll/tests/test_vocal_text_roll.py` (7 tests).

## Coverage written

**IR parsing (real corpus).**
1. B9 known answers: 3,587 texted notes (from 3,588 `<lyric>` — one is a bare
   `<extend>`), 405 melismas.
2. `syllabic` values are exactly the known four.
3. **Words reconstruct across notes** — `begin`/`middle`/`end` runs rejoin, the
   run closes cleanly, the first eight words are pinned, and the joined text
   contains "Freude, schöner Götterfunken". This is the assertion that fails if
   `syllabic` were dropped or mis-ordered; counts alone would still pass.
4. Every B9 extend accompanies its own text.
5. Instrumental works (Bach, Schubert, Sym5) carry no lyrics and no extends.
6. Validation: unknown `syllabic` rejected; empty-string lyric rejected; lyric
   participates in the deterministic sort (so `validate()` is stable for two
   notes differing only in text).
7. Parser edge cases via synthetic MusicXML: a second verse is dropped **with a
   warning** naming the verse; an unknown `<syllabic>` warns and keeps the text;
   a bare `<extend/>` does not surface as an empty lyric.

**Roll codec.**
8. lyric/syllabic/extend survive encode→decode; an instrumental note does not
   acquire a lyric.
9. `_canonical` sees the text: stripping it, or changing the syllable, the
   syllabic class, or the extend flag each makes the key differ.
10. Repeated syllables are interned — 200 copies of "der" cost < 700 bytes.
11. Non-texted works stay canonical-identical (the change is additive).
12. B9 round-trips all 3,587 lyrics + 405 melismas and the words rejoin after
    the round trip.

## Verification that the pipeline can now catch the loss

Before this change, `_canonical` omitted the fields, so the chain would have
passed with the text silently gone. Verified directly: with the fields in the
key, stripping one lyric from a decoded work makes `_canonical(decoded) !=
_canonical(source)`.

## Known-answer amendment

`test_roll_gaps.py::test_beethoven9_roundtrip_budget` pinned B9's payload at
168,281 bytes. Amended to **177,088** (+8,807; +5.2%) for 3,587 lyrics + 405
melismas, with the reason recorded in the test and in `FORMAT_SPEC.md` §4.6.
Non-texted works moved **zero** bytes — the golden fixtures did not need
regenerating, which is the evidence that the encoding is additive.

## Known gaps (acceptable, and deliberately scoped)

- **Single verse only.** Extra verses are dropped with a warning. Multi-verse
  works (hymns, opera) need a verse dimension; decomposed, not hidden.
- **No hyphenation rules, language tags, or verse numbering.** The carrier
  stores the syllable as written; MusicXML's `<humming/>`, `<laughing/>` and
  similar markers are not distinguished from text.
- **Standalone `<extend/>`** (no `<text/>` on the same note) is kept as
  `lyric=None, extend=True`. That state is legal in MusicXML but does not occur
  in the corpus, so it is covered by a parser test rather than a corpus pin.
- **MIDI vocal text.** MIDI lyric meta events (`0x05`) are still not read. The
  corpus's MIDI sources (Byrd) are untexted, so there is no evidence to drive
  the behaviour; recorded as a gap rather than guessed.
- **The chain still proves IR→IR, not source→IR.** That scope is now stated
  explicitly in `docs/pipeline.md` §Phase 1 instead of being implied — the
  parser-coverage caveat is documented rather than left for a future reader to
  rediscover.

## Revision during implementation: multi-verse is corpus evidence, not a gap

Mid-build I asserted in the parser docstring that verse 1 was "the only one
the corpus uses". **That was wrong**, and the S1 golden-vector gate caught it:
`bwv227.7` failed verification, carrying a dropped-verse warning.

Decompressing the chorales showed **`bwv227.7` and `bwv227.11` each set two
verses per note** (17 notes carry verse 2). That is not an edge case: a
Lutheran chorale sings one tune to several texts, so dropping verse 2 loses
half the words of a movement.

So the carrier gained a verse dimension:

| Where | What |
|---|---|
| IR | `Verse(number, lyric, syllabic, extend)`; `Note.verses` holds 2..n, verse 1 stays on the note's own fields |
| Roll | presence bit 8 for "has verses"; a per-verse flags byte so the record is self-describing; syllables interned |
| Canonical keys | `_canonical` (roll) and S1's `to_canonical` both include verses, so a dropped verse fails the chain |
| Validation | verse numbers >= 2, unique per note, known syllabic |

The test asserting the old behaviour (`test_extra_verses_are_dropped_with_a_warning`)
was **inverted** to `test_additional_verses_are_carried`, with the reason in its
docstring — the same "a red test after a fix can be the deliverable" situation
as #317's chain test.

### Second finding: the canonical surface was bloating every work

Emitting `lyric: null` / `verses: []` on every note grew **all 13** golden
vectors ~38%, including the ten instrumental works. Fixed by emitting the
fields only when present, which restored the honest property: the ten
instrumental vectors are **byte-identical** to before this change, and only the
three texted works grew.

### Third finding: a duplicated hardcoded measurement

`tools/muse_explorer/generate.py` quick mode carried a hardcoded
`(168281, 0.0024)` for B9 that duplicated the real encode — so the freshness
tripwire disagreed with itself the moment the encoding changed. Replaced with a
derived value; both paths now compute the same expression.
